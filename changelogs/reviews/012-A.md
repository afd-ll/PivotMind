## 二、发现问题

### P0 — 刚引入的性能退化（应立即修复）

**位置**：`src/multi_topology.c:1327-1336`

语义跨拓扑投票段使用了 O(n) 线性扫描 `cross_links` 数组（~12 万条）：

```c
for (int cl = 0; cl < master->cross_link_count; cl++) {
    CrossTopologyLink* link = &master->cross_links[cl];
    if (link->from_topo_id == sub->topo_id &&
        link->from_node_id == pid &&
        link->to_topo_id == TOPO_SEMANTIC) { ... }
}
```

但项目中 `cross_adj` 邻接表早已构建完成并投入使用：

- `associative_reasoning.c:190` — `cross_adj[adj_idx]` 做 O(1) 查找
- `causal_reasoning.c:2349` — 同上
- `multi_topology.c:1602` — `topology_walk_cross` 也在用

**影响**：每步每个候选节点 × 每个路径节点 × 12 万条扫描。在节点平均出度 ~600、路径长度 ~20 的情况下，每步额外开销约 600 × 20 × 120000 = 14.4 亿次循环。

**修复方向**：改用 `cross_adj` 邻接表，将 O(n) 降到 O(avg_cross_degree)。

### P1 — 架构级性能问题

#### P1-1：激活传播全节点遍历

**位置**：`src/dialog_system.c:76-139` — `dialog_topo_worker()`

```c
for (int n = 0; n < sub->net->node_count; n++) {
    ReasoningNode* node = sub->net->nodes[n];
    if (!node || node->activation < 0.15f) continue;
    for (int c = 0; c < node->connection_count; c++) { ... }
}
```

**问题**：每跳传播遍历子拓扑中全部节点（~23712 个），激活低于 0.15 的跳过但仍在循环中。可用激活队列（active set）只遍历已激活节点。

**影响**：9 层子拓扑 × 全部节点 = 对话主循环最大开销源。

#### P1-2：上下文关联度模糊匹配 O(n²)

**位置**：`src/cognitive_controller.c:125-136` — `calc_context_activations()`

```c
for (int n = 0; n < sub->net->node_count; n++) {
    for (int i = 0; i < tok_count; i++) {
        if (strstr(cc->current_input, node->concept) || ...)
```

**问题**：对每个节点×每个 token 做 `strstr` 双向匹配。且内层循环用 `strstr(cc->current_input, ...)` 对整个输入做扫描而非单个 token，语义上也有问题——这会让短 token 匹配到输入中任意位置的子串。

**修复方向**：预建 token→节点哈希映射，或用 AC 自动机做多模式匹配。

#### P1-3：递归锁开销

**位置**：`src/trace_wisdom_topology.c:112`

```c
pthread_mutexattr_settype(&mutex_attr, PTHREAD_MUTEX_RECURSIVE);
```

**问题**：递归锁比普通锁慢约 3 倍。若调用链中不存在同一线程重复加锁的场景，应降级为普通锁。

#### P1-4：剪枝模块冒泡排序

**位置**：`src/pruning.c:28-37`（及多处）

```c
for (size_t i = 0; i < num_zeros; i++) {
    for (size_t j = i + 1; j < mask->size; j++) { ... }
}
```

**问题**：用冒泡排序找 threshold，O(k × n)。应该用快速选择算法降到 O(n)。

### P2 — 架构设计缺陷

#### P2-1：拓扑边数单调增长，无剪枝机制

**位置**：README §已知局限 3 已记录

`pruning.c` 只针对 Tensor（神经网络权重），不处理拓扑边。拓扑边在赫布学习中只增不减——低权重边、长期未激活边、置信度接近 0 的边永远占着内存。

**影响**：12 万跨拓扑连接、308 万内部边，随训练轮数持续增长。

**建议**：实现拓扑边淘汰策略（三选一或组合）：
- 置信度阈值淘汰（`connection_confidences < min_confidence`）
- LRU 淘汰（`last_activated_time` 超时清理）
- 边权重下限（`connection_weights < min_weight`）

#### P2-2：意图向量初始值无先验区分

**位置**：`src/cognitive_controller.c:56-59`

```c
for (int i = 0; i < MAX_SUBTOPOS; i++) {
    cc->intent_weights[i] = 1.0f / MAX_SUBTOPOS;
```

**问题**：10 维均匀初始化 0.1。词汇拓扑和语义拓扑应该在初始阶段有更高权重（它们是回答生成的主要信号源），而文化拓扑、概念拓扑初始权重应较低。

#### P2-3：global_visited 跨拓扑语义丢失

**位置**：`src/dialog_generate.c:72-98`

`global_visited` 只按节点 ID 标记，不考虑节点所属子拓扑。不同子拓扑中相同 ID 的节点可能含义不同（虽然当前设计是各子拓扑节点 ID 独立），但从 visited 位图看是同一语义空间。
