# Changelogs

PivotMind 项目变更日志。按版本号排列，一个版本一个文件，扁平存放。

## 版本号规则

```
X . Y . Z
│   │   └── 当前架构下的变动次数（0.0.Z）
│   └────── 大型架构版本号（0.Y.0）
└────────── 发布版本号（X.0.0）
```

| 段位 | 含义 | 递增条件 |
|------|------|---------|
| `X.0.0` | 发布版本 | 达到可对外分发的稳定里程碑 |
| `0.Y.0` | 架构版本 | 发生大型架构变化（新增脑区、重构核心管线等） |
| `0.0.Z` | 变动计数 | 当前架构下每次修改递增 |

**示例**：`1.4.23` 表示第 1 版发布、第 4 版架构、第 4 版架构下的第 23 次变动。

PivotMind 当前处于第 0 版发布（预发布阶段），经历过 4 次大型架构迭代。

## 文件命名

```
NNN-简短描述.md
```

`NNN` 为三位零填充内部编号（000~035），版本号记录在文件内部标题中。

示例：`016-competitive-queue.md`、`035-web-fetch-refactor.md`

### 内部编号 ↔ 版本号对照

| 编号 | 版本 | 说明 |
|------|------|------|
| 000~015 | 0.0.1 ~ 0.0.16 | 原型期 |
| 016~021 | 0.1.0 ~ 0.1.5 | 第一版架构 |
| 022~029 | 0.2.0 ~ 0.2.7 | 第二版架构 |
| 030~033 | 0.3.0 ~ 0.3.3 | 第三版架构 |
| 034~045 | 0.4.0 ~ 0.4.7 | 第四版架构 |

## 格式规范

```markdown
# X.Y.Z — 标题

> **日期**: YYYY-MM-DD | **类型**: [新增/修复/重构/优化/清理]

## 概述

简述做了什么。

## 核心变更 / 修复内容

改动内容（列表、表格、代码块等均可）。

## 改动文件

| 文件 | 变更 |
|------|------|

## 编译验证

验证结果。
```

### 类型标签

| 标签 | 含义 |
|------|------|
| 新增 | 新功能、新模块 |
| 修复 | Bug 修复 |
| 重构 | 代码结构改进，无功能变化 |
| 优化 | 性能优化 |
| 清理 | 代码清理、删除死代码 |

## 报告规则

当先出审查/诊断报告时，报告文件存放在 `reports/` 目录，命名与 changelogs 同编号：

```
reports/NNN-简短描述.md
```

如果后续基于该报告进行了修复：
- 修复内容写入对应的 `changelogs/NNN-修复描述.md`
- **同步更新报告文件**，在原报告末尾追加已完成项的标记和修复提交信息

示例：
```
reports/044-architecture-review.md     ← 先出审查报告
changelogs/044-p0-dialog-test.md       ← 修复 P0 项后写 changelog
reports/044-architecture-review.md     ← 在原报告中追加"P0 已完成，提交 abc1234"
```
