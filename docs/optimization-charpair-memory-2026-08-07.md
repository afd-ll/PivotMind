# 优化方案：字符对记忆化 + 学习入口队列化 + 聚类增量（v0.5.9 候选）

> **日期**: 2026-08-07 | **状态**: 待拍板 | **作者**: 玄枢架构讨论（用户拍板）

## 一、背景

v0.5.8 修复了锁纪律问题（漏锁/锁内重活），但暴露深层问题：**字符对表是"永久记账本"**——

- 字符对（相邻字共现统计）无限膨胀：pair_count 185 万，2M 槽负载 91%，每次查找变慢，内存 64MB 常驻
- 早期方案（截断/按 last_seen 遗忘）均被否决：
  - 截断 = 人为阉割统计（治标）
  - 按"最近出现"遗忘 = "你好"几天不露面就被删（学了个寂寞）
- 用户拍板方向：**字符对 = 记忆痕迹**，与字节点/边同构（权重/激活值/效价/巩固度），走记忆系统生命周期，冷冻与记忆结合

## 二、设计原则

1. **无限制器**：不设人为截断/限流/429——负载由结构自消化
2. **记忆 = 生命周期**：一切统计都是记忆，有形成→巩固→降权→（不删除）的过程
3. **遗忘 ≠ 删除**：长期不出现只降权（activation 衰减），痕迹永不删——再出现即回弹
4. **冷启动安全**：新生记忆不被误杀（清理只清"未巩固+长期不活跃"）
5. **类脑同构**：与 Hebbian 边权（共现计数+饱和曲线）、冻结机制（is_cooled）、三重记忆（短期/长期）统一哲学

## 三、字符对记忆实体

### 3.1 数据结构（PairEntry 升级）

```c
typedef struct {
    char   a[8];            // 第一个字
    char   b[8];            // 第二个字
    int    co_count;        // 权重（共现计数）
    float  valence;         // 效价 -1.0 ~ +1.0（默认 0，从语料/反馈涌现）
    float  consolidated;    // 巩固度 0~1（Hebbian 渐近，反复出现上升）
    int    last_seen;       // 最近出现 tick（驱动激活衰减）
    int    tier;            // 0=短期（工作记忆） 1=长期（巩固后）
    int    used;
} PairEntry;                // ~36 字节（现 ~28，+8B/对，2M 槽 ≈ 72MB）
```

**激活值不单独存**——由 `last_seen` 推导：`activation = decay(tick - last_seen)`，省字段且天然衰减。

### 3.2 生命周期机制

```
出现（_ar_find_pair 命中/插入）:
    co_count++
    consolidated += 0.02 × (1 - consolidated)     // Hebbian 渐近线 1
    last_seen = tick
    if consolidated ≥ 0.5 → tier = LONG           // 晋升长期

长期不出现:
    activation 衰减（由 last_seen 推导）→ 查询权重降权
    但 consolidated / co_count / 痕迹保留 → 永不删除

再次出现:
    last_seen 更新 → activation 回弹（记忆提取成功）
```

### 3.3 表满清理（唯一删除路径）

```
触发：pair_count ≥ 表上限（2M）
扫描全部：
    跳过 tier = LONG（长期记忆，永不删）
    跳过 last_seen 距今 ≤ 窗口（5 万 tick ≈ 14h @1s/tick）——近期活跃
    清除：未巩固 + 长期不活跃的短期对（自然消退）

效果：表容量 = 长期对 + 活跃短期对，自然平衡，不再无限涨
冷启动：表不满 → 不触发 → 零误杀
```

### 3.4 效价（valence）

- **来源 1（启发）**：与情感种子词（好/坏/喜/悲…）的共现加权——先占位
- **来源 2（反馈）**：对话 `/feedback` correct/wrong 信号沿共现路径传播（玄枢已有反馈机制）
- **用途**：生成端词选择的情感倾向（"你好"正 / "死"负）——v0.5.9 先存字段，统计方法后续深化

## 四、学习入口队列化（/learn）

**现状**：`handle_learn` 每请求 spawn detached 线程 → 喂料期 35 线程稳态

**改**：固定 worker（2 个）+ 任务队列（链表，容量 256，满则丢最旧）
```
HTTP 请求 → 入队 → 立即返回 202
learn worker ×2 → 串行消费队列 → article_process_line
```

- **线程数恒定**：主 + 脑干 + 感知 worker + learn worker×2 + 自学 = ~7（非 35）
- **无 429/限流**——队列满了丢最旧（最近的学习请求优先，类工作记忆丢弃策略）
- **与感知 worker 同构**：玄枢所有外部学习入口统一队列化

## 五、聚类增量（POS 池）

**现状**：try_emerge 每 500 次分类全量 256² 相似度矩阵（2-5 秒）

**改**（分两步）：
- **v0.5.9 先降规模**：池上限 256→64（聚类 64² = 4096 次，单次快 16 倍），保留全矩阵算法（简单可靠）
- **v0.6 候选增量**：新词只与已有簇中心比较（classify_soft 已是此逻辑），try_emerge 只对"匹配不上的池"做轻量聚类——取消全矩阵

## 六、与记忆系统/冻结的集成

| 玄枢组件 | 对齐方式 |
|---|---|
| 短期记忆（MemorySystem short_term） | tier=SHORT 对（词发现的工作记忆） |
| 长期记忆（LongTermMemory） | tier=LONG 对（巩固后的词知识） |
| 海马体（hippocampus_consolidate） | 巩固节奏可挂字符对巩固扫描（后续） |
| 冻结（is_cooled） | consolidated 高 = 冻结态：存盘导出稳定长驻，不参与清理 |
| 存盘/加载 | PairEntry 新字段随 brain_state.dat 格式版本 v2 导出（向后兼容读 v1） |

## 七、参数表（初始值，观察后调）

| 参数 | 值 | 说明 |
|---|---|---|
| 巩固增量 | 0.02 × (1-c) | 每次出现，渐近线 1 |
| 晋升阈值 | consolidated ≥ 0.5 | → tier=LONG |
| 短期清理窗口 | 5 万 tick | ~14h @1s/tick，出现过的短期对不删 |
| 表上限 | 2M 槽 | 不变，清理后自然维持 |
| 池上限 | 256→64 | 聚类快 16 倍 |
| learn worker | 2 个 | 队列化后 |
| 学习队列容量 | 256 | 满丢最旧 |

## 八、实施计划

**Phase 1（v0.5.9）**
1. PairEntry 升级 + find/出现逻辑（consolidated/last_seen/tier）
2. 表满清理（只清短期+不活跃）
3. /learn 队列化（learn worker×2）
4. 池上限 256→64
5. 存盘格式 v2（向后兼容）

**Phase 2（观察 1-2 周后）**
6. 效价统计（情感种子/反馈传播）
7. 增量聚类（取消全矩阵）
8. 海马体巩固节奏挂字符对

## 九、验证方案

1. **冷启动**：喂少量语料 → 无清理、无丢失（pair_count 单调涨）
2. **长期不删**：喂"你好"类词 → tick 快进模拟 → 确认 tier=LONG 保留、仅 activation 降
3. **表满清理**：压力喂料至 2M → 清理只清短期不活跃 → 长期全保留
4. **线程恒定**：喂料中线程数稳定 ~7
5. **回归**：喂料/存盘/加载（v1 兼容）/对话/POS 涌现正常
6. **内存**：RSS 增量 <10MB（PairEntry +8B/对）

## 十、风险与回退

| 风险 | 应对 |
|---|---|
| PairEntry 变大（+8B×2M=16MB） | 可接受（板子 4GB）；若紧张降表上限 1.5M |
| 表满扫描 2M 遍历 | 周期触发单次 ~100ms，可接受 |
| 队列化丢最旧 = 丢学习请求 | 类工作记忆丢弃策略（最近优先），喂料脚本间隔大不受影响 |
| 格式 v2 与 v1 兼容 | 读 v1 时新字段置默认值（consolidated=0.5 保守晋升） |
| 回退 | 全部改动集中在 article_reader.c / pivotmind_gateway.c / emergent_pos.c，git 分支可整体回退 |
